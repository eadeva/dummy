# PTK GitHub workflow authoring

First follow the [project discovery and execution guide](../../../docs/guides/agent-guide.rst). Use the project's installed PTK and configured jobs, variants, paths and permissions; do not assume the consumer contains PTK's source checkout or its example `verify` job.

## Establish the graph and artifact contract

1. Read [GitHub Actions](../../../docs/guides/github-actions.rst) for supported commands, action inputs and limitations, and [matrix setup](../../../docs/guides/cx-matrix.rst) for identity and destination fields. Confirm `ptk maintainer gen-workflows --help` and `ptk maintainer matrix --help` exist in the selected release. If unavailable, explain the version mismatch; do not invent commands or silently upgrade PTK.
2. Find the owning `workflows/NAME.ptk.yml` and all called jobs. If no PTK workflow exists, use [local workflow authoring](../ptk-workflow-authoring/SKILL.md) to create it first. Preserve dependency intent, invocation IDs, typed parameters and owner `repo_variants` mappings. Each target repository/job can appear only once in a PTK workflow. Reserve `setup` for the generated setup job.
3. Inspect actual output-producing commands and explicitly declare useful files/directories on their producing steps or job, with optional `artifact_type`. See [job authoring](../ptk-job-authoring/SKILL.md) and [artifact manifests](../../../docs/guides/artifacts.rst). Never infer outputs from a build folder or add cache merely for uploads. Require portable, disjoint repository-relative destinations; do not declare both a directory and its child. Use a stable output filename when a tool supports it. Do not invent output globs or a separate PTK `inputs` mapping.
4. Inspect `artifactory_paths.ptk.yml`: base URL, repository, event routes and job suffixes. Reuse the setup-resolved producer URL, including its timestamp, on upload and download. Actual paths come from completed jobs, not setup. Ask only for missing project choices needed to finish the requested template: action repository/ref, runner, container image, caller events, checkout strategy or secret names. Leave explicit TODOs where the user wants a template; never insert live credentials or plausible-looking invented service URLs.

## Generate and review

5. Run `ptk validate`, then `ptk maintainer gen-workflows NAME` with the discovered repository prefix and approved `--action-repository` / `--action-ref`. The file belongs in the workflow owner's `.github/workflows`. If it exists, the command warns and leaves it unchanged: review and edit the existing project-owned file within the request, rather than deleting it to force regeneration. Generating files does not dispatch jobs or transfer artifacts.
6. Keep `on: workflow_call`. The first `setup` job must run `ptk maintainer matrix --workflow NAME --format github`; all execution jobs must declare `needs: [setup, ...producer_invocations]`. Select each job's matrix from `setup.outputs.matrix_<invocation>`. Never use the last-finishing matrix job's outputs to identify a producer. The generated consumer waits for every producer variant, then selects its matching variant. GitHub `max-parallel` limits each matrix, not the whole workflow.
7. In each execution job, preserve checkout, download when there are producer needs, `ptk-run-job`, then `ptk-upload`. Pass `toJSON(needs)` and the setup row's producer selectors to download; `setup` is metadata, not a producer. Pass job, one variant, typed parameter JSON and working directory to run-job. Upload uses that step's `uploads-json`, the producer row and setup upload URL. Keep `output-paths` as JSON; do not parse console output or guess the latest log directory. Never invoke `ptk workflow run` in CX.
8. Complete or clearly label runner/Docker TODOs. The Linux job container must already contain a matching PTK release, Python 3.12+, Bash, curl and project tools. Configure registry access/mounts only when required. Use secret references for the technical user and token. Pass `additional_properties` as JSON to upload without overriding producer identity. Pin action refs to approved commits before production use; do not treat the generator's development-branch default as the project's release policy.
9. For detected VMRs, keep VMR-checkout TODOs instead of ordinary checkout in **every** job, including setup, until the project's checkout mechanism is supplied. Recreate the configured member layout and revisions. Set the workflow owner `project-directory`; preserve matrix working directories and mapped producer variants. Downloads restore paths beneath the producing repository, which can differ from the consumer repository. For Git-based version sources, ensure checkout provides the required history/tags. Do not invent a `repo init` manifest URL.

## Validate and hand off

10. Inspect the generated graph and action wiring against the PTK workflow. Preview `matrix --workflow NAME` in an appropriate context only after checking configured version commands: matrix export can execute version discovery. A local maintainer can use `--ci` and `--event EVENT` for a relevant preview. Do not bypass role checks or change maintainers to run validation. Use YAML/action linting when available; a parsed file alone does not prove hosted execution succeeds.
11. Verify that files upload directly, directories use ZIP, and downloads restore original relative paths after SHA256/identity checks. Scope defaults to GitHub repository/run ID; use the same explicit scope on both sides when overriding it. Missing manifests, unsafe paths, symlinks and overlapping restores fail. Successful earlier steps may expose artifacts after later failure; whole-job outputs require complete success. Preserve cancellation and failure behavior, and do not claim partial outputs are complete. Project authors own artifact correctness, retention and cache decisions.
12. Report the workflow path, dependency/variant mapping, declared outputs, completed checks and remaining TODOs. Distinguish generation, local validation and actual hosted execution. Running the pipeline, accessing secrets or uploading artifacts needs to be within the user's requested scope. Do not dispatch a workflow simply to prove the template was written.
