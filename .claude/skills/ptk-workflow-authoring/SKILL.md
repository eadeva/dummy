# PTK local workflow authoring

First follow the [project discovery and execution guide](../../../docs/guides/agent-guide.rst). Apply it even when this skill is invoked directly; examples are syntax references, not project defaults.

1. Read [workflows](../../../docs/guides/workflows.rst) and the target repositories' `.main.ptk.yml` files. Locate `repository.config_path`; use `ptk repos` from a VMR root to verify aliases. Read existing job definitions before composing them. PTK workflow execution is local-only. For a native CX pipeline, use [GitHub workflow authoring](../ptk-github-workflows/SKILL.md); the generated GitHub jobs execute individual PTK jobs.
2. Put each workflow body in `workflows/<name>.ptk.yml` under the owner's configuration folder. For workspace workflows use `workflows/<name>.ptk.yml` at the VMR root and use `job: ALIAS:JOB` on every invocation. Keep repository-owned names separate; do not merge equal names from different repositories.
3. Build a `jobs` mapping keyed by unique invocation IDs. Use `{job: JOB}` for an owner job or `{job: ALIAS:JOB, params: {PARAM: VALUE}}` for a VMR call. Invoke each target repository/job only once; duplicate targets are rejected even when parameters differ. Define distinct jobs when distinct configured invocations are needed. Discover target jobs and parameter types. Select one owner variant; use its `repo_variants` mappings for other repositories. Workspace-owned workflows have no variant model. Never put secret values in workflow parameters.
4. Use `needs: ID` or `needs: [ID, ID]` for prerequisite invocation IDs. Omitted/empty `needs` makes a job immediately eligible; YAML order does not serialize execution. Validate unknown IDs, self-dependencies and cycles. Use dependencies for shared outputs, hardware or services. Unordered calls cannot share a repository/job/variant output or a `python.project` environment, even with one worker. `max_workers` bounds active calls. Do not author workflow `steps`, `parallel`, nested groups or separate `repo` fields; steps inside jobs use a separate `needs` graph.
5. Failed or skipped prerequisites block their dependent chain; independent branches continue. Use `continue_on_error` only when dependents should run despite this invocation failing. Reports retain the failure. Cancellation and skipped calls are never tolerated. Keep step retries, timeouts and cleanup in the job.
6. Run `ptk validate`; use the discovered workflow help/execution route for inspection with `--graph` or `--dry-run` (which includes the graph automatically). Maintainer workflows need the maintainer prefix. At a VMR root select member workflows as `ALIAS/NAME`; under `ptk ALIAS workflow`, use `NAME`. Preflight validates every call; resolve missing prerequisites in the target repository before execution. Use a job's `--dry-run` for command-level details.
7. Run `ptk workflow run NAME` when executing the requested jobs is authorized. Check exit status, workflow summary and child reports. Workflow `open_report` defaults to `always`; use `on-errors` for failures (including tolerated failures and imported report errors) or `null` to omit successful full-report opening. Active errors still open dedicated diagnostics locally. CX and dry runs never open it. Child jobs keep their own policies. Read [reporting configuration](../../../docs/guides/configuration.rst) when imported results or job report opening need adjustment.
8. Workflow names are also direct commands (`ptk NAME`), listed in help. Local job/workflow collisions prompt; CX chooses the job. Scripts must use the explicit `run` or `workflow run` form. A workflow summary selected for opening suppresses child openings; otherwise child policies apply after completion.
9. Keep outputs explicit and project-owned. Optional reuse requires declared outputs plus `cache: true`; root calls execute, while eligible dependent calls may reuse unchanged content. `--no-cache-ptk` bypasses reuse across the workflow. Read [output reuse](../../../docs/guides/output-reuse.rst); never infer outputs or cache from build directories.
10. When generated tasks are in scope, run `ptk maintainer sync tasks` and its `--check` mode. For a VMR, generate root workflow tasks and member job/workflow tasks where needed. Preserve user tasks. Use [the complete example](../../../examples/workflows/app/config/workflows/verify.ptk.yml) and [its repository workflow](../../../examples/workflows/app/config/workflows/all.ptk.yml) as tested syntax, not as assumed repository names or jobs. See [editor integration](../../../docs/guides/editor.rst) for interactive terminal browser links and the external-browser setting.

A workspace-owned `audience: maintainer` workflow uses `maintainers.ptk.yml` at
the VMR root. Member jobs retain their own role checks. Lists contain login IDs;
`PTK_ROLE=maintainer` does not grant access. Editor task generation is maintainer-only;
use `--users-only` for shared tasks. See [configuration](../../../docs/guides/configuration.rst).
