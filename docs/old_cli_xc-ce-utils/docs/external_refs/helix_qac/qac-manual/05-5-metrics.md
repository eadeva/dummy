5 | Metrics
Metrics Overview
A metric is a measure of some quantifiable attribute of source code. No single metric will provide a comprehensive
indicator of code quality, but each provides a different view of aspects such as complexity, readability, residual bugs, or
testability.
Helix QAC for C calculates 68 different metrics, of two types:
 n Function-Based Metrics - Generated for all functions with a full definition
 n File-Based Metrics - Generated for each analyzed file
Metric values are calculated automatically during the analysis process and are recorded in the .arc file.
Note:
Additional metrics—including project metrics and STM29—are generated by the cross-module analysis
component (RCMA).
All metrics, except STLIN and STTPP, are calculated after conditionally included groups have been handled by pre-
processing. Additionally, when the -ppmetrics,-ppm configuration option is enabled, header file contents will also affect
the calculation of metrics.
Metric Thresholds
Most metrics can be directly linked to warning messages. By specifying a metric threshold, any generated metric value
falling outside these limits will result in an analysis warning. Thresholds can be set as part of configuring a coding
standard.
These thresholds can be specified with the -threshold option as a relational expression, in the following format:
-threshold metric op value[:[prefix_]message]
metric
The metric name as it appears in the Metrics chapter of the QAC, QAC++ or RCMA Component
 Manual (as appropriate).
operator
A relational operator (<, <=, ==, >, >=).
value
An integer or a floating point value for which  Helix QAC for C will generate a warning message
if the threshold is exceeded.
prefix_
An optional identifier that is used to associate the generated message with the compliance
module that the message is being generated for.
message
The warning message that is generated, as an optional entry. This message number should
refer to a dedicated warning message, specified by the user.
If you do not specify a message number for a threshold,  Helix QAC for C will issue warning 4700. For example:

Threshold Order
During analysis,  Helix QAC for C will compare metric values against the respective thresholds in the order in which they
have been specified. If the relational expression is TRUE, it will issue a warning and abandon further checks for that
metric.
As a result, the order in which threshold options are specified is important. If you want  Helix QAC for C to issue different
warnings for increasing degrees of severity, you should ensure that your thresholds are specified in decreasing order of
severity. For example:
Code Example:
 STCYC>=30:5003
 STCYC>=20:5004
 STCYC>=10:5005
The above thresholds, in the order given, could be used to enforce three levels of Cyclomatic Complexity. If the metric
value is 35, user-defined warning message 5003 will be generated: if the metric value is 25, warning message 5004 will
be generated: and if the metric value is 15, warning message 5005 will be generated.

STAKI Akiyama's Criterion
This metric is the sum of the cyclomatic complexity (STCYC) and the number of function calls (STSUB). Although this is
not an independent metric, it is included on account of its use in documented case histories. See Akiyama1 and
Shooman2 for more details. The metric is calculated as:
STAKI = STCYC + STSUB
STAVx Average Size of Statement in Function
These metrics (STAV1, STAV2, and STAV3) measure the average number of operands and operators per statement in
the body of the function. They are calculated as follows:
STAVx = (N1 + N2) / number of statements in the function
where
N1 is Halstead’s number of operator occurrences.
N2 is Halstead’s number of operand occurrences.
The STAVx metrics are computed using STST1, STST2 and STST3 to represent the number of statements in a function.
Hence there are three variants: STAV1, STAV2 and STAV3, relating to the respective statement count metrics.
This metric is used to detect components with long statements. Statements comprising a large number of textual
elements (operators and operands) require more effort by the reader in order to understand them. This metric is a good
indicator of the program’s readability.
Metric values are computed as follows:
STAV1 = (STFN1 + STFN2) / STST1
STAV2 = (STFN1 + STFN2) / STST2
STAV3 = (STFN1 + STFN2) / STST3

STCAL Number of Functions Called from Function
This metric counts the number of function calls in a function.
It differs from the metric STSUB, in that only distinct functions are counted (multiple instances of calls to a particular

STGTO Number of Goto statements
Some occurrences of goto simplify error handling. However, they should be avoided whenever possible. According to the
Plum Hall Guidelines, goto should not be used.
STKDN Knot Density
This is the number of knots per executable line of code. The metric is calculated as:
STKDN = STKNT / STXLN
The value is computed as zero when STXLN is zero.
STKNT Knot Count
This is the number of knots in a function. A knot is a crossing of control structures, caused by an explicit jump out of a
control structure either by break, continue, goto, or return. STKNT is undefined for functions with unreachable code.

STM07 Essential Cyclomatic Complexity
The essential cyclomatic complexity is obtained in the same way as STCYC Cyclomatic Complexity, but is based on a
’reduced’ control flow graph. The purpose of reducing a graph is to check that the component complies with the rules of
structured programming.
A control graph that can be reduced to a graph whose cyclomatic complexity is 1 is said to be structured. Otherwise,
reduction will show elements of the control graph that do not comply with the rules of structured programming.
The principle of control graph reduction is to simplify the most deeply nested control subgraphs into a single reduced
subgraph. A subgraph is a sequence of nodes on the control flow graph which has a single entry and exit point. McCabe1
identifies the following four cases that result in an unstructured control graph:
 n a branch into a decision structure;
 n a branch from inside a decision structure;
 n a branch into a loop structure;
 n a branch from inside a loop structure.
However, if a subgraph possesses multiple entry or exit points then it cannot be reduced. The use of multiple entry and
exit points breaks the most fundamental rule of structured programming.
The following example below has an STM07 value of 4:

STM29 Number of Functions Calling this Function
This metric is defined as the number of functions calling the designated function. The number of calls to a function is an
indicator of criticality. The more a function is called, the more critical it is and, therefore, the more reliable it should be.

STPBG Residual Bugs (STPTH-based est.)
Hopkins, in Hatton & Hopkins1 investigated software with a known audit history and observed a correlation between
Static Path Count (STPTH) and the number of bugs that had been found. This relationship is expressed as STPBG.
STPBG = log10 (STPTH)
STPDN Path Density
This is a measure of the number of paths relative to the number of executable lines of code.
STPDN = STPTH / STXLN
STPDN is computed as zero when STXLN is zero.
STPTH Estimated Static Program Paths
This is similar to Nejmeh’s2 NPATH statistic and gives an upper bound on the number of possible paths in the control
flow of a function. It is the number of non-cyclic execution paths in a function.

statement and for the nested structures. NPATH is the product of:
 n NPATH( sequence of non control statements ) = 1

 n NPATH(while) = NPATH( body of while) + 1

 n NPATH(for) = NPATH(body of for) + 1
 n NPATH(switch) = Sum( NPATH(body of case 1) ... NPATH(body of case n) )

NPATH Strict Estimated Static Program Paths
This is to Nejmeh’s1 NPATH statistic and gives an upper bound on the number of possible paths in the control flow of a
function. It is the number of non-cyclic execution paths in a function.
The NPATH value for a sequence of statements at the same nesting level is the product of the NPATH values for each
statement, including the branches of logical expressions, and for the nested structures and subexpressions. NPATH is
the product of:
 n NPATH( sequence of non control statements ) = Product( NPATH(expression statements))
 n NPATH(if) = NPATH(controlling expression) + NPATH(body of then) + NPATH( body of else)
 n NPATH(while) = NPATH(controlling expression) + NPATH(body of while) + 1
 n NPATH(do while) = NPATH(controlling expression) + NPATH(body of while) + 1
 n NPATH(for) = NPATH(initialization expression) * (NPATH(controlling expression) +
 n NPATH(body of for) + NPATH(increment expression) + 1)
 n NPATH(switch) = Sum( NPATH(body of case 1) ... NPATH(body of case n) )
 n NPATH(?: expression) = NPATH(condition) + NPATH(true branch) + NPATH(false branch)
 n NPATH(expression) = (number of logical operators) + 1

STRET is the count of the reachable return statements in the function, plus one if there exists a reachable implicit return
at the } that terminates the function.

The number of function calls within a function. Functions with a large number of function calls are more difficult to

small value indicates that there may not be enough comments, which can make a module difficult to understand.

STDEV Estimated Development (programmer-days)
This is an estimate of the number of programmer days required to develop the source file. Unlike COCOMO statistics,
which are based solely on the number of lines of code, this estimate is derived from the file’s difficulty factor. It is a more
accurate measure of the development time, especially after the scaling factor has been adjusted for a particular software
environment.
STDEV = STEFF / dev_scaling where dev_scaling is a scaling factor defined in -prodoption development::scaling.
The default is 6000.
STDIF Program Difficulty
This is a measure of the difficulty of a translation unit. An average C program has a difficulty of around 12. Anything
significantly above this has a rich vocabulary and is potentially difficult to understand.
STDIF = STVOL / ((2 + STVAR) * log2 (2 + STVAR))
STECT Number of External Variables Declared
This is a measure of the number of data objects (not including functions) declared with external linkage. It is an indication
of the amount of global data being passed between modules. It is always desirable to reduce dependence on global data
to a minimum.

STHAL Halstead Prediction of STTOT
This metric and also STZIP are predictions (derived from the vocabulary analysis metrics STOPN and STOPT) of what
the value of STTOT should be. If they differ from STTOT by more than a factor of 2, it is an indication of an unusual

unusually rich vocabulary. The two metrics are computed as follows:
