GitHub Actions and callable workflow templates
==============================================

Generate native GitHub workflows from PTk's configured graph and ``cx.ptk.yml``::

   ptk maintainer gen-workflows verify
   ptk maintainer gen-workflows
   ptk maintainer gen-workflows verify --replace-unmarked

For a workflow ``verify`` the repository owning it receives:

* ``.github/workflows/call-verify.yml``: a callable workflow whose ``setup`` job
  exports the matrices, followed by one job per workflow entry that calls the
  entry's job workflow with ``secrets: inherit``;
* ``.github/workflows/call-<job>.yml`` for every PTk job of the workflow
  (``call-<alias>-<job>.yml`` for a job of another VMR repository). It runs one
  PTk job for every row of a matrix and can also be called on its own.

With no names, all discovered workflows are generated. Generation is
maintainer-only and does not execute jobs or contact Artifactory.

Every generated file starts with ``# Generated by ptk maintainer gen-workflows.``
Files with that line are replaced on the next generation; files without it
(hand-written or reworked: remove the line to keep manual changes) are left
alone with a warning. ``--replace-unmarked`` copies such files to
``.github/workflows_backup/<date>/`` first and then replaces them.

CX configuration
----------------

``cx.ptk.yml`` in the configuration directory supplies everything the files need:

.. code-block:: yaml

   technical_user: tet6yh            # secret names: <PROJECT>_<TECHNICAL_USER>_<CREDENTIAL>_<FIELD>
   runner_group: ${{ vars.RUNNER_GROUP }}
   image: null                       # default: docker.image
   artifactory_credential: null      # default: docker.credential
   pmt:
     repository: XC-CE/pmt           # default
     version: v26.45.00
   vmr:                              # only for members of a virtual monorepo
     manifest_url: https://github.example.com/org/product_manifest.git
     app_id: 1400
     private_key: GITHUB_APP_PRIVATE_KEY
     owner: org

* Jobs run on ``runs-on: {group: runner_group}`` in ``container: image``. The
  container logs in with ``docker.login_user`` (``{user}`` replaced by the
  technical user) and the token of ``artifactory_credential``.
* Secrets keep PTk's CX convention. The token of ``artifactory`` for project
  ``Firmware`` and technical user ``robot`` is the secret
  ``FIRMWARE_ROBOT_ARTIFACTORY_TOKEN``. The run step of a job workflow maps
  exactly the credentials referenced by its steps (all fields except
  ``user_field``) to environment variables of the same names. Optional
  credentials are declared as not required. Create the secrets in GitHub and call
  ``call-<workflow>.yml`` with ``secrets: inherit``.
* Checkouts use ``<pmt>/.github/actions/checkout-or-repo-init@<version>``: a full
  clone with tags for standalone repositories, or git-repo with the GitHub App
  for VMR members. A VMR member without ``cx.vmr`` cannot be generated. VMR
  workflows accept ``manifest-branch`` and ``checkout-ref`` inputs. ``cx.checkout``
  (``uses``/``with``) replaces that step, for example with a project-owned
  repo-init action; the GitHub App secret is then not declared.
* Artifacts move with ``ptk maintainer cx download`` and ``ptk maintainer cx
  upload`` inside the job container, logged in as the technical user.

Setup and dependencies
----------------------

The ``setup`` job of ``call-<workflow>.yml`` checks out the sources and calls::

   ptk maintainer matrix --workflow verify --format github

The setup export supplies ``matrix_<invocation>`` and ``has_jobs_<invocation>``
for each workflow invocation. Each row contains only execution information,
parameters, its repository directory, upload destination and producer selectors.
Runtime output paths remain absent. All routes share one setup timestamp, so
consumers use exactly the destinations selected for their producers, including
job-specific suffixes.

Every entry declares ``needs: [setup, ...configured_producers]`` and passes its
matrix, ``toJSON(needs)``, ``max-parallel`` (``max_workers``) and
``continue-on-error`` to its job workflow. A consumer waits for all variants of its
producer jobs, then downloads only its selected producer variant. Workflow job
keys identify producing PTk jobs directly. GitHub IDs are generated as
``job_<jobname>`` for local jobs and ``repo_<reponame>_job_<jobname>`` for
qualified jobs. Existing underscores remain unchanged. Workflow validation rejects
combinations that produce the same ID, naming both targets and asking for a
repository alias or job rename. For example, ``a_job_b:c`` and ``a:b_job_c`` both
produce ``repo_a_job_b_job_c`` and cannot share a workflow. These IDs also name
per-job matrix outputs; display names retain the original keys. The setup job
remains ``setup``, so a PTk job named ``setup`` is allowed.

Owner ``repo_variants`` mappings apply to VMR producers. Identical mapped calls
are deduplicated; conflicting parameters/dependencies for the same producer
identity fail setup and require selecting one owner variant. Ineligible variant
rows and their dependent rows are pruned; all configured job definitions remain in
YAML. Each execution calls one PTk job, never a PTk workflow.
``continue_on_error`` tolerates the run step, followed by an explicit
required-output contract check. It does not tolerate output-contract or transfer
failures.

Job workflow steps
------------------

``call-<job>.yml`` runs these steps for every matrix row:

#. Checkout and ``git config --global --add safe.directory '*'`` (the container
   runs as root; the checkout belongs to the runner user).
#. For rows with producers: ``ptk maintainer cx download`` fetches and verifies
   the producers' outputs and restores them.
#. ``ptk [-V variant] [--no-cache-ptk] [maintainer] run <job> --params <file>``
   with the job's credential secrets. JSON reaches the shell through environment
   variables, never through the script text.
#. ``ptk maintainer cx upload`` uploads the declared outputs, also after a failed
   run for outputs of completed steps.
#. With ``continue-on-error``: the required-output contract check.

The ``cx`` commands are hidden machine interfaces. Like ``matrix`` they are
allowed in CX without a maintainer login and grant no other capability.

Artifact transfer
-----------------

* ``upload`` reads the completed job's upload manifest through the private
  result handoff (never a "latest" log). Directories are ZIP-compressed,
  including nested files and empty directories, with ordinary Unix permission
  bits. Every file is uploaded with curl and its own properties (repository,
  job, version, commit, variant aliases, step, optional artifact type and
  ``additional-properties``, which may not replace identity fields).
* With ``name`` in ``artifactory_paths.ptk.yml`` (per event or route too), files
  land directly in the destination as ``<name>.zip`` for a single output or
  ``<name>_<artifact_type or file name>.zip``, plus ``<name>.ptk-manifest.json``.
  Example: ``name: ${run.job}_${run.variant}_${version.current.value}``. Without
  ``name``, files go to ``ptk/<hash>/<run>/<index>/`` below the destination, where
  the hash covers the producer identity and the run scope.
* The manifest lists relative paths, kinds, SHA256 checksums and properties and
  is uploaded last, so consumers never see a partial set.
* ``download`` accepts only producers listed in the caller's ``needs``. It
  verifies identity, scope (GitHub repository and run ID) and every checksum
  before replacing outputs at the producer's original repository-relative
  location below the checkout root (in VMRs the matrix supplies the producing
  repository directory). An output inside another directory output of the same
  producer is restored with that directory. No server-wide search or "latest
  artifact" heuristic is used.
* Uploading the same name again (a re-run, or the same commit and branch)
  overwrites the files; the technical user needs overwrite permission.
* A failed job without outputs uploads nothing (``outputs-valid=false``); a
  successful job without a usable manifest fails the upload step.

Constraints
-----------

* HTTPS is required. Credentials reach curl through stdin and PTk through
  environment variables, never on command lines.
* Symlinks, special files, absolute/traversing paths and unsafe ZIP entries are
  rejected. Overlapping destination paths across declarations/producers fail
  before restoration. Select disjoint output paths across producers; within one
  producer a directory output may contain another output.
* Downloads replace each declared destination, removing stale directory
  contents. Do not declare source directories as outputs. Downloads and ZIPs are
  validated/staged before replacement, but replacement of multiple outputs is
  not transactional; an OS failure can leave a partially restored set.
* POSIX permission bits are preserved, not ownership, ACLs, extended attributes
  or timestamps as a reproducibility contract. ZIP symlinks are unsupported.
  Staging needs space for downloaded archives and expanded contents.
* Missing producer manifests/checksum failures fail the consumer. A tolerated
  failed producer may expose successful step outputs, but their completeness
  remains the project's responsibility.
* The generated workflows target Linux job containers. The image must contain
  PTk, Bash, Git and curl. Container construction, remote publishing policy
  and Artifactory retention are not managed here. No live credentials or
  service access is required for generation or the automated transfer tests.

Composite actions
-----------------

PTk's former composite actions ``ptk-run-job``, ``ptk-upload`` and
``ptk-download`` remain under ``.github/actions`` for existing hand-written
workflows; generated workflows no longer use them.

See :need:`REQ_Sw_CI_GENERATION`, :need:`REQ_Sw_GITHUB_ARTIFACTS` and
:need:`DD_GITHUB_ACTIONS` for the requirements and decisions.

Declared outputs and dependency checks
--------------------------------------

All declared outputs are required. PTk fails a successful producer whose declared
outputs are missing or not regular files/directories; its upload manifest carries
``outputs_valid: false`` and ``cx upload`` refuses to publish it. Required
output failures block local workflow consumers even with ``continue_on_error``.
A job with no declarations may still publish an empty manifest. Downloads validate
published identity, paths and payload hashes; they are not ``when`` predicates.
Project commands remain responsible for semantic content and freshness.

Portable job conditions and generated matrices
----------------------------------------------

Job ``when`` uses only CX and variant context, including feature/component symbols
and ``vh`` data. Runner OS/environment and job parameter/variable namespaces are
step-only; evaluating them in setup would not predict another runner correctly.
Every configured job remains defined in the generated YAML. Conditions filter
variant rows, never delete job definitions. For each owner variant, setup removes
false job rows and transitively removes
consumers needing those rows. Other branches remain. Cross-repository conditions
use the mapped producer repository's resolved variant. Deduplication and conflicting
producer-input checks still apply after pruning.

Setup exports ``has_jobs_INVOCATION`` alongside ``matrix_INVOCATION``. Generated
job guards check setup success, this flag, cancellation and producer success before
matrix expansion. An empty matrix therefore skips its GitHub job instead of
attempting an invalid expansion. All jobs still depend on setup. Producer selectors
contain only eligible dependencies. PTk evaluates the condition again when executing
the job. Use the same configuration revision and CX context in setup and execution.
A whole producer matrix must succeed before consumers run; one variant failure
blocks all of that invocation's consumers, as with GitHub needs semantics.

Regenerate after upgrading PTk; files carrying the generated marker are replaced.
Test both enabled and disabled variants. Hosted execution remains a project
validation step; local YAML tests do not run GitHub Actions.

The stage step exposes ``outputs-valid``. With ``continue-on-error`` the job
workflow tolerates ordinary run-step failure but explicitly requires this output
to be true; missing or invalid handoffs fail closed. Upload/download errors are
never tolerated by that option. Do not replace this with job-wide GitHub
``continue-on-error``, which could release consumers after missing outputs.
