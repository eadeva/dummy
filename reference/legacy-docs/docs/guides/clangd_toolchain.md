# Parallel clangd CMake Toolchain (PNG-style)

## Why

When a project's *real* compiler is not clang / GCC / MSVC (typically
Green Hills `cxtri.exe`, TASKING `ctc`, IAR `iccarm`, Renesas, TI), the
`compile_commands.json` produced by the native CMake configure is full of
vendor-specific flags (`-cpu=tc1v162`, `--gnu_asm`, `-list`, `-frigor=fast`,
...) that clangd cannot parse. Result: a flood of `drv_unknown_argument`
warnings, no jump-to-definition across MCAL/OS/HSM boundaries, no hover
types, no usable clang-tidy.

The fix mirrors what `png-gen1` does with GN: run a **second,
configure-only** CMake invocation that targets the same source tree but
uses a generated clang toolchain file. The two builds coexist:

```
_build/<variant>/                  <- real Green Hills firmware build
  build/
    compile_commands.json          <- promoted to clangd version (see below)
    compile_commands.native.json   <- original Green Hills version, kept for ref
    xc_ce_definitions.cmake        <- variant defines, auto-generated
    clangd/                        <- parallel clangd configure (no link)
      xc_ce_clangd_toolchain.cmake <- generated by xc-ce-utils
      compile_commands.json        <- clang-readable database
      clang_vfs/                   <- optional MemMap VFS overlay
```

The real firmware build is unaffected. clangd, IDE Go-to-Definition, and
clang-tidy now use the clang-friendly database transparently.

## What runs when

The hook lives in `RBCMakeWrapper.setup()` and fires *after* the native
configure on developer machines. CI environments (`GITHUB_ACTIONS=true`,
`CI=true`, or `JENKINS_HOME` set) skip this IDE-only configure by default.
Set `clangd_toolchain.run_in_ci: true` to opt a CI analysis job in. Flow:

1. Native `cmake -GNinja -S <src> -B _build/<variant>/<action>` runs.
2. xc-ce-utils calls `_maybe_configure_clangd_toolchain()`:
   * Resolves `config/clang/clang_conf.yml::clangd_toolchain.enabled`
     (`config/clang/` is the common **default** location — the actual
     config root is the parent directory of wherever `main_conf.yml`
     resolves; see [main_conf.yml's Discovery
     Order](config_files/main_conf.md#discovery-order)).
   * `auto` → detects the project's compiler family from
     `config/cmake/compiler_toolchain.cmake` (or env hints
     `TOOLBASE_GREENHILLS_IFX`, `TASKING_HOME`, `IAR_HOME`).
   * Skips silently for clang / GCC / MSVC native builds.
   * Generates
     `_build/<variant>/<action>/clangd/xc_ce_clangd_toolchain.cmake`.
   * Runs `cmake -GNinja -S <src> -B _build/<variant>/<action>/clangd
     -DCMAKE_TOOLCHAIN_FILE=...`.
   * Promotes the clang database over the native one, backing up the
     native as `compile_commands.native.json`.
3. The existing `_refresh_clang_compile_commands()` updates the
   `_build/compile_commands.json` link that `.clangd` points at.

Failures at any step are warnings only — the firmware build never fails
because of a clangd configuration issue.

## How to enable

Add to `config/clang/clang_conf.yml`:

```yaml
enabled: true

clangd_toolchain:
  enabled: auto              # auto | true | false
  run_in_ci: false           # false by default; true opts CI into generation
  target_triple: auto        # auto | "i386-pc-windows-gnu" | "arm-none-eabi" | ...
  extra_isystem: []          # extra -isystem paths for vendor SDKs
  guard_variable: XC_CE_CLANGD_TOOLCHAIN
```

Defaults live in
[`xc_ce_utils/clang/templates/clang_conf.defaults.yml`](../../xc_ce_utils/clang/templates/clang_conf.defaults.yml).

## Guarding vendor-only constructs

Some CMake constructs only make sense for the real linker (custom targets
that consume the linked ELF, `cxtri --version` probes, `-lnk0=...` link
options). Wrap them so the clangd configure can succeed:

```cmake
if(NOT XC_CE_CLANGD_TOOLCHAIN)
    add_custom_target(generate_elf_adx ALL
        COMMAND ${CMAKE_ADDRESS_CALCULATOR} ...
        DEPENDS ${PROJ_NAME}
    )
endif()
```

The guard variable name is configurable via
`clangd_toolchain.guard_variable`.

## Compatibility shim headers

The generated toolchain force-includes (`-include`) a curated set of
shim headers so clang accepts vendor extensions:

```
config/clang/compat/
  greenhills/   ghs-intrinsics-compat.h, ghs-attributes-compat.h, ghs-os-compat.h
  ifx/          ifx-mcal-compat.h
  autosar/      escrypt-hsm-compat.h
  project/      project-specific shims (not overwritten on regen)
```

Base shims are owned by xc-ce-utils and refreshed every run. Project
shims under `compat/project/` are appended *after* the base shims, so a
project shim wins when re-declaring something. Typical project shim
candidates: supplier BSW intrinsics (Vector SIP, ETAS, EB tresos),
CycurHSM / EVITA primitives, custom AUTOSAR `MemMap.h` / `Compiler.h`.

## MemMap VFS overlay

When AUTOSAR `*_MemMap.h` headers expand vendor pragmas that even
`-include` shims cannot neutralise, the toolchain can additionally
inject `-ivfsoverlay <vfs.json>` (port of png-gen1's `mk-vfs.py`).
Each listed MemMap header is virtually replaced by an auto-generated
stub that only `#undef`s `MEMMAP_ERROR`; the real on-disk header is
untouched, so the firmware build keeps working. Enable per-project:

```yaml
clangd_toolchain:
  vfs:
    enabled: auto                     # auto | true | false
    memmap_headers:
      - "SW/**/*_MemMap.h"
```

Output: `_build/<variant>/<action>/clangd/clang_vfs/{vfs.json, stubs/...}`.
Generation is best-effort — failures degrade to "no overlay" and
never break the configure. See the
[Clang Tooling Stack §6](clang_stack.md#6-memmap-vfs-overlay) for the
full design, JSON schema, and stub-template override.

## Per-variant defines

The generated toolchain `include()`s
`_build/<variant>/build/xc_ce_definitions.cmake` (auto-emitted by
`xc-ce-utils DefinitionsGenerator`). This propagates every `BO_*` /
`RB_*` variant define to the clangd build without parsing
`CMakeCache.txt` or duplicating the definitions list.

If the native build for the target variant has not run yet, the
generated toolchain emits a CMake warning and continues with
unconditional defines only.

## Target-triple choice

Without `--target=`, clang defaults to the host triple
(`x86_64-pc-windows-msvc`), giving wrong `sizeof(long)`, `sizeof(void*)`,
and `sizeof(size_t)` versus the embedded ABI. Defaults per family:

| Compiler family | Default target_triple    | Rationale                |
| --------------- | ------------------------ | ------------------------ |
| Green Hills     | `i386-pc-windows-gnu`    | TriCore is 32-bit (matches Green Hills cxtri ABI for `int`/`long`/`void*`) |
| TASKING         | `i386-pc-windows-gnu`    | TriCore 32-bit           |
| IAR             | `arm-none-eabi`          | Arm Cortex-M             |
| Renesas         | `arm-none-eabi`          | Arm-targeted RX/RH       |
| TI              | `arm-none-eabi`          | Arm-targeted             |

Override per-project via `clangd_toolchain.target_triple`.
