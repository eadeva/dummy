# B | Metric Output File

B | Metric Output File
Overview
Helix QAC for C++ stores a semantic representation of the translation source file. For example:
n include file usage,
n function calls,
n derived classes,
n references to objects with external linkage,
n definitions and declarations of all functions, variables, macros, labels, tags, and typedefs,
n function control flow structure information,
n memory allocation kind,
n metric values,
n #pragma directives,
n use of exceptions,
n use of literals.
A lua API and interpreter, qax2lua, allows access to the non-human readable .arc file content. See Using the lua API
for more information.
Using the lua API
Release Compatibility
The Helix QAC lua API is subject to change from release to release, and is not guaranteed to be source- code compatible
from one release to the next.
Support for specific features depends on the version of Helix QAC and the API that you use.
Architecture of the API
The qax2lua utility includes a lua 5.4.4 interpreter and version 1.0 of the API.
Application Programming
Running a lua script
qax2lua can be used to access information in the arc output format. The -script option and at least one data source
are required. The valid command lines are:
1. qax2lua -script <script.lua> [ -file <outputfile> ] [ -outputpath <path> ] <source_
file>
2. qax2lua -script <script.lua> [ -file <outputfile> ] [ -outputpath <path> ] -cmaf
<project_output> <source_file>
3. qax2lua -script <script.lua> [ -file <outputfile> ] [ -outputpath <path> ] -cmaf
<project_output>

The -script parameter specifies the lua script to be processed. This parameter is required in all variants. The optional
-file option specifies the name of the file that the script output is written to.
The use of -cmaf affects the output of the script as follows:
n The first variant has access to per translation unit analysis results only. Other information, such as project metrics
associated with functions or classes will not be available, eg: STM29.
n The second variant has access to both per translation unit and project analysis. Also available is the name of the
project output file and the project wide metrics.
n The third and final variant has access to project analysis results only. In this variant, the project name can be
used to access the project wide metrics
Note:
Metrics associated with functions and classes that are generated by RCMA, for example STM29, are only
available when the second variant, that is both -cmaf and a source_file is used.
Additional Script Paths
The LUA_PATH environment variable is used when searching for Helper scripts referred to from the primary script.
qax2lua appends the folder of the primary script path to the end of the LUA_PATH ensuring that files local to the primary
script will be found.
Directory used for output files when using -file
The optional -file parameter specifies that the output be written to <outputfile>. If not specified then the output is
written to STDOUT.
The output for the interpreted script is redirected through calling the lua function io.output( outputfile ). This
call redirects the output from calls to io.write to <outputfile>. Calls to print will still be written to STDOUT.
The output directory used when creating the -file <outputfile> option is determined as follows:
n If <outputfile> is an absolute path, then output is written to that exact path, otherwise,
n if qax2lua has been invoked with a <source_file>, that is variants 1 or 2 above, then output will be written to
the OS appropriate joining of the -outputpath configuration option and source_file, finally,
n if qax2lua has been invoked without a <source_file>, that is variant 3 above, then output will be written to
the OS appropriate joining of the directory of the -cmaf configuration option and source_file.
Additional _file variables
fileArgOpt
The name of the output file when -file is specified
fileArgOutputOpt
The handle to the file for output when -file is specified
Output Encoding
The output encoding of strings produced by qax2lua, either to STDOUT or via the -file option, is UTF-8.

Availability of Records
The reading and processing of the parsers output can be expensive. Records are read, processed and stored in memory
in order that they are available to the script. Where a script requires a subset of the parser output, the processing and
storing of unused records is a waste of effort.
To take advantage of this, 'qax2lua' limits the records stored to the minimal set required by the specified script. This is
achieved by first tokenizing and searching the content of the argument to the '-script' option for references to the
global functions and tables.
Note:
If a global function or table is used exclusively from a file referenced indirectly, for example via the
'require' function, then its name must also appear somewhere in the main script, for example in a lua
comment. Otherwise the records for that API will not be available when the script is run. The tokenization
stage will not scan lua short-strings or the body of C/C++ style comments in the script, for example: /* ...
*/ or //.
